# 我早就知道要异步协作，直到有了 awaiting 才做到

"异步协作能提高效率" 这句话，我很早就同意了。

我的 [y-agent](https://luohy15.com/zhs/y-agent-introduction) 本来就是并行的：一个 todo 开一条 trace，往下派 plan / impl / review 子 session，同时推进五六个任务，技术上没有任何障碍。

但我实际的一天不是这么过的。派完任务之后我在干嘛？切 chat。这个做完了吗？那个卡住了吗？轮到我了吗？一圈刷下来没什么变化，过十分钟再刷一圈。

**任务是异步的，我的注意力不是。** 这就是为什么我知道归知道，一直没做到。

## 缺的不是并发，是交接点

想清楚之后，我要的东西其实很小：系统得在两种状态之间给我一条明确的线。

一种是 **它在干活**，这时候我不该被打扰，也不该去看。另一种是 **轮到我了**，要么需要我拍一个只有我能拍的板，要么活干完了等我验收。

之前没有这条线，所以我只能靠轮询去猜。猜的成本不是那几分钟，是注意力：只要我还惦记着 "那个任务不知道跑到哪了"，我就没法专心做别的事。并行的是任务，串行的是我。

## awaiting：一个状态，就是我的收件箱

最后落到的实现比我一开始想的简单得多。**不是做一个收件箱系统，而是给任务加一个状态：这件事现在需不需要我。**

因为 trace id 就是 todo id，一个任务底下不管展开成多少个 chat，这个状态只有一个。**我处理的是任务，不是 chat。** 于是收件箱不是新东西，就是任务列表的一个筛选：

```bash
$ y todo list --status awaiting
  ID  Name                                                Status    Chat
----  --------------------------------------------------  --------  ------
3502  Build a shared household finance dashboard with Wu  awaiting  eacfbb
3492  Fix social analyst falling back to news             awaiting  -
```

`pending` / `active` / `awaiting` / `completed`，就多这么一档。进出也没有专门的命令，和改任何一个状态一样：`y todo status <id> awaiting` 进去，`y todo status <id> active` 出来。而且大多数时候我连出来这一步都不用管：我在那个任务的 chat 里回一句话，它自己就回到 active 了。

进入这个状态的时候，系统给我发一条消息。所以我也不用刷这个列表。

空的，就说明没有任何事在等我。这句话听起来很轻，但它才是整套东西真正的产出：**我终于可以放心地不看了。**

## 我的注意力被放出来了

回过头看，awaiting 没让任何一个 agent 变快。它只做了一件事：**把任务的执行和我的注意力解耦了。**

具体到我一天的形状：

**之前是一问一答。** 我和一个 agent 同步推进一件事，它跑的时候我在看它跑。中间那些等待既不够长到能去做别的事，又足够长到把思路打断，于是就这么耗着。

**现在是派发加处理队列。** 想清楚要什么，一次派出去几件，然后就不管了。我不知道它们跑到哪了，而且我不需要知道。等被通知打断的时候，我一次性处理一批：这个要拍板、那个要验收、这个方向不对退回去重做。

几个附带的变化，我觉得比那个机制本身更值得说：

- **我的输入形态变了。** 以前大量精力花在盯过程、随时纠偏；现在集中在两头，前面把需求说清楚，后面认真验收。中间那段我不再参与，这也逼着我把需求想得更清楚，因为没法靠中途补救了。
- **我开始舍得做那些慢的事。** 以前一件要跑 40 分钟的任务，我会本能地想 "太慢了算了"，因为那 40 分钟我得陪着。现在派出去就不占我时间，长任务的心理成本几乎归零。
- **空收件箱变成一个可以信任的信号。** 这是最舒服的一点。以前 "好像没事了" 永远带着一点不确定，得再扫一圈才安心；现在它是一条查询的结果。收件箱空了我就真的去休息，不用在脑子里挂着五件半成品。
- **代价是放弃过程的控制感。** 不看过程就意味着有些事会往错的方向跑十几分钟，等我看到的时候只能退回重做。这个成本是真的，但比起我以前那种 "全程盯着、还是得返工" 的模式，划算太多。

## 结尾

这套东西不新。异步协作、工作队列、把中断变成可批处理的收件箱，都是别人早就做过的。

但 "知道异步能提效" 和 "亲手把自己的工作方式改成异步" 是两回事。我卡在中间卡了很久，卡住我的不是理解，是缺一条明确的交接线。补上之后，之前那个理解才第一次真的能执行。

**方法未必是新的，它对我的意义是新的。**
