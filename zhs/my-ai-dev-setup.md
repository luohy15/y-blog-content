# 我的 AI 开发配置：统一入口，云端工作环境

![架构图：桌面、平板和手机通过 Web 或 Telegram 接入同一个 y-agent；Claude Code 执行任务，侧边连接 EC2 文件和 RDS 数据库；自建 relay 与 Claude、GPT、Grok 模型来源是概念关联，各家接入方式和订阅限制需分别确认。](https://cdn.luohy15.com/blog/images/my-ai-dev-setup.svg)

最近看到一篇[《我的 agent 配置方案》](https://knowledge.you-find.me/articles/9c37a536-d589-4508-8f14-870f19b24735)，把自己的工具按 Client、Memory、Runtime、Gateway 和模型来源拆开讲。我觉得这个视角挺好，也照着梳理一下我现在这套。

先说我想解决的问题：**有个需求时，我不想先打开电脑、找到项目、启动 Terminal，再开始跟 agent 聊。** 手机上能把需求说清楚，它就应该能开始干。等轮到我做决定或验收时，再叫我。

所以我把工作环境留在 EC2 上，用 y-agent 作为统一入口，不管是在桌面还是手机上。Telegram 也接进来，作为一个更好用的对话输入框。代码、笔记和任务记录留在自己的系统里，不跟着某一个聊天窗口走。

## 在波士顿试过一次：只带平板，能不能工作

之前[去波士顿](https://luohy15.com/zhs/2026/09/08/boston-2026)时，我没带 laptop，只带了 iPad 和 iPhone。当时在游记里写：

> 顺便当个实验，看只用平板能不能把活干完

结论是可以。这套配置确实撑起了出差期间的工作，不只是手机上发个消息、看一眼进度。

当然，效率肯定没有在 laptop 或大屏幕上高。但差别主要在我这一端的显示和交互，具体 agent 干活没有区别。它还是在同一个云端环境里读代码、改文件、跑命令，不会因为我手里换成了 iPad，就少了什么工具。

朋友 L 哥戏称这套系统叫 **waywork**，取的是 work 和 on the way 的意思。只需要 Telegram 和 Safari，在路上也能把活干了。

这个名字还挺贴切。不是说平板能全面替代电脑，而是临时需要工作的时候，不用先找回那台装好了开发环境的 laptop。

## 先看配置

| 这一层管什么 | 我现在用什么 |
| --- | --- |
| 从哪里发需求、看结果 | y-agent 作为桌面和手机的统一入口，接入 Telegram 作为对话输入框 |
| 项目背景和任务状态存哪里 | EC2 上的文件 + RDS 里的数据库 |
| 谁读代码、改文件、跑命令 | Claude Code |
| 模型请求怎么接出去 | 自建 relay service，维护自己的 fork |
| 模型来源 | Claude / GPT / Grok 的订阅 |

这不是五个服务串成的一条流水线。文件和数据库是工作时按需读写的资料，不是模型请求必须经过的一站。模型来源也不等于 Runtime：用 Claude Code 执行任务，和选择哪个模型，是两个不同的问题。

下面按一次需求怎么走来讲。

## 入口：y-agent 是统一入口，Telegram 是输入框

[y-agent](https://github.com/luohy15/y-agent) 是我的 universal 入口。不管是在桌面还是手机上，跟 agent 对话、管理任务、看上下文和结果，都围绕这一套系统。

Telegram 的角色更简单：一个更好用的对话输入框。它已经把聊天交互做得很顺手，我接进来用，就不用花太多时间打磨自己的输入框了。

所以不是桌面用 y-agent、手机用另一套 Telegram 系统。Telegram 只是接入 y-agent 的一种方式，任务和上下文还是同一份，换个设备也不用重新介绍项目。

比如想改一个功能，我先把要什么说清楚。需要持续跟踪的工作会记成一个 todo，后面的讨论、方案和改动都围绕这个任务展开，而不是聊完一段之后再想办法从历史消息里捞。

我在意的不只是能不能远程聊天。只把 Terminal 搬到手机上，最后还是我盯着它干活。我想要的是：**发出去的是一个任务，回来的是需要我处理的事。**

## 记忆：文件放 EC2，结构化数据放 RDS

一个新 session 接手时，最麻烦的不是让它开始写代码，是让它知道前面已经决定了什么。

我的做法比较朴素。代码、项目约定、方案和 review 结论放文件里；任务状态、聊天记录，以及它们之间的关联放数据库里。文件在 EC2，数据库用 RDS。

文件适合留完整的内容。为什么这么设计、哪些方案没选、下一步从哪继续，写成一篇 note，比散在几十轮聊天里好找。

数据库适合回答具体的问题：这个任务有哪些 session？现在轮到谁？之前那篇方案关联的是哪个任务？Agent 通过 `y` CLI 查询这些数据，不需要我手动复制一遍。

比如一个需求中间换了执行它的 session，接手的那个先读 todo，再沿着关联去读方案和进度。它不需要继承前一个 session 的所有对话，但得找到继续工作所需的事实。

所以我这里说的 memory，不是“把所有聊天塞回 prompt”。**存下来是一回事，下次能按需找到是另一回事。** 我用任务 ID 把同一件事的记录串起来，再用 tag 找相关主题。这个在[之前的文章](https://luohy15.com/zhs/trace-and-tag)里展开过。

## 执行：Claude Code 干活，任务编排放外面

真正读代码、编辑文件、跑命令的是 Claude Code。我没有自己再写一套 coding agent 的执行循环。

但一个需求要怎么拆、派给哪个 session、结果怎么交接，我放在 y-agent 这一层。

简单的事，一个 session 做完就行。复杂一点的开发需求，通常会先有方案，再实现，再 review。每一步可以是新的 session，读同一个任务下的材料，不必把所有阶段挤在一个越来越长的对话里。

这些 session 也不是几个固定坐在那里的“员工”。需要做什么，就加载对应的 skill；任务复杂了，再往下拆。Skill 里放的是这一步该怎么做的约定。

我把编排放外面，一个很实际的原因是：**子任务的聊天记录也得归我管。** 我能看到它们的输入和产出，需要时能进去纠偏，而不是只收到主 session 对过程的转述。

当然，拆开不代表自动变好。需求没说清楚，多个 session 也能一起做错；review 也不能代替我的验收。编排解决的是怎么组织工作，不是替我决定到底要做什么。

## 接入：自建 relay，模型来源和工作环境分开

模型接入这一层，我用的是自建的 [claude-relay-service](https://github.com/luohy15/claude-relay-service)，维护了一个自己的 fork。模型订阅有 Claude、GPT、Grok。

这里我刻意把几件事分开：

- y-agent 管我怎么交付任务、找回上下文。
- Claude Code 管一个 session 怎么调用工具把活干下去。
- Relay 管模型请求的接入和转发。
- 订阅是模型能力的来源，不是存项目状态的地方。

我不想每换一个模型，就连工作入口和任务记录一起换掉。至少代码在哪、方案在哪、哪些事还没做完，这些不应该依赖我这次选了哪家模型。

不过，分层不等于所有组合天然兼容。接口、工具调用和各家订阅的使用限制，仍然得分别确认。这里列的是我自己的配置，不是一份“买了订阅就能统一当 API 用”的教程。

自建也有边界。工作记录由我自己保存，不代表模型推理在本地完成；送给模型的上下文仍会离开这台机器。多一个 relay，也多一层需要自己维护的服务。

## 串起来：我负责两头，中间让它跑

拿一个普通功能需求举例，我希望它这样走：

1. 我从 Telegram 或 Web 说清楚需求，留下一个可跟踪的任务。
2. Agent 读取项目和已有材料，必要时先出方案。
3. 执行 session 在工作目录里改代码、做检查，review session 再看改动。
4. 方案、review 结论和进度都挂回任务，不只留在各自的聊天里。
5. 到了需要我决策、批准发布或验收的时候，再把任务交回来。

发布是单独的边界。Review 通过不等于可以直接上线；要发哪一版、包含哪些改动，需要说清楚，再由我批准。

任务需要我时会进 `awaiting`，也就是我的收件箱。还在执行，或者只是等另一个子任务，就不应该叫我回来点一下“继续”。

这部分我也[单独写过](https://luohy15.com/zhs/async-collaboration-awaiting)。对我来说，它比多接一个模型更影响日常使用：我终于不用靠反复切 chat，猜现在是不是轮到我了。

## 代价也很直接

这套东西不是装完就不用管了。EC2、数据库、relay、客户端，以及它们之间的状态衔接，都成了我自己的维护工作。出了问题，不能只怪模型。

任务记录留在自己手里，也意味着备份、权限和数据边界得自己负责。模型换得动，不代表整个系统就没有迁移成本。

如果只是偶尔让 AI 帮忙改几行代码，直接用现成工具会省事很多。我愿意折腾这一套，是因为我不只想要一个更好用的聊天框，而是想把它接进自己每天处理事情的方式里。

回头看，配置表里最容易变的是模型，最值得留下的是项目背景、任务记录和交接方式。

**我想保住的是这套工作习惯：随时能交代一件事，过程有地方可查，轮到我时再回来。**
